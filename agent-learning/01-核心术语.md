# 第一站：核心术语

---

## 1. LLM（大语言模型）

### 是什么
Large Language Model。你用的 DeepSeek、Claude、GPT 都是 LLM。

### 本质
一个"超级预测器"——你给它一段文字，它预测最合理的下一段文字。它不是真的"理解"或"思考"，而是基于训练数据做概率预测。

### 你的项目里
`deepseek-v4-Flash` 就是你的 LLM。它负责翻译论文、提炼要点。

---

## 2. Token（令牌）

### 是什么
LLM 不认字，只认 Token。它是 LLM 处理文本的最小单位。

### 换算关系（粗略）
- 1 个中文字 ≈ 1-2 个 Token
- 1 个英文单词 ≈ 1-2 个 Token
- 标点符号也算 Token

### 为什么重要
- LLM 按 Token 收费（输入 + 输出都要算）
- `max_tokens` 参数限制模型最多输出多少 Token

### 你的项目里
`max_tokens: 2000` = 限制输出约 1000-1500 个中文字。翻译摘要够用，写长文不够。

---

## 3. Prompt（提示词）

### 是什么
你给 LLM 的输入文本。Prompt = 你说的话。

### 两种类型

| 类型 | 放什么 | 特点 |
|------|--------|------|
| **System Prompt** | 角色、规则、输出格式 | 一次设置，整个对话有效 |
| **User Message** | 本次任务的具体数据 | 每次请求都可以变 |

### 你的项目里
```
System Prompt: "你是工业设计/人因工程领域的学术研究助手..."
User Message: "标题: xxx / 作者: xxx / 摘要: xxx"
```

### Prompt 工程的本质
设计"怎么说才能让 LLM 稳定地做你想让它做的事"。
- 角色要具体（不是说"你是助手"，而是"你是X领域的Y角色"）
- 格式要明确（不是说"返回JSON"，而是给出完整 JSON 示例）
- 防幻觉要有兜底（"如果缺失则标注'本文未明确说明'"）

---

## 4. Context Window（上下文窗口）

### 是什么
LLM 一次能"看见"的最大文本量。超出窗口的内容会被截断或遗忘。

### 你的项目里
你用的模型 `deepseek-v4-pro[1m]`，`[1m]` = 100 万 Token 的上下文窗口。可以把整本《三体》一次塞进去。

### 重要原则
上下文窗口大 ≠ 什么都往里塞。
- 越长 = 越贵（Token 消耗）
- 越长 = 越慢
- 越长 = 模型注意力越容易分散，可能忽略关键信息

---

## 5. Tool Call / Function Call（工具调用）

### 是什么
让 LLM 不只是"说话"，还能"操作外部世界"。

### 工作流程
```
LLM 输出："我要调用 tool_search_paper(keyword='动态办公椅')"
     ↓
你的程序执行这个函数，得到结果
     ↓
把结果返回给 LLM
     ↓
LLM 根据结果继续思考下一步
```

### 和 Chatbot 的区別
- Chatbot：只会说话
- 有 Tool Call 的 Agent：能搜资料、发邮件、操作数据库、移动文件

### 你的项目里
**目前没有真正的 Tool Call。** 你的流程是代码硬编排的——采集→处理→入库，每一步都是你写死的，不是 LLM 自己决定的。这是 "Chain"，不是 "Agent"。

### 举例：真正的 Tool Call
```
用户："帮我把这篇动态办公椅的论文加入项目并翻译"

LLM 自主决策：
  Step 1 → 调用 tool_search_paper("动态办公椅")  // 先找到论文
  Step 2 → 调用 tool_link_project(paper_id, "office-chair")  // 加入项目
  Step 3 → 调用 tool_translate(paper_id)  // 翻译摘要
```

## 6. Memory（记忆）

### 是什么
Agent 记住信息的能力。分三层：

| 层级 | 存什么 | 存活时间 | 举例 |
|------|--------|---------|------|
| **短期记忆** | 当前对话的上下文 | 一次会话内 | "你刚才说要找动态办公椅的论文" |
| **长期记忆** | 结构化数据 | 持久化（关掉程序也在） | 你的 SQLite 里 890 篇文献 |
| **工作记忆** | 当前任务的中间结果 | 单次任务内 | 批处理循环里"已处理到第 15 篇" |

### 你的项目里
- 短期记忆：无（你的 Agent 没有对话功能）
- 长期记忆：SQLite 数据库（890 篇文献的结构化数据）
- 工作记忆：`process_batch` 循环里的 `success/failed` 计数器

### 为什么 Memory 重要
没有记忆的 Agent = 每次对话都是"初次见面"。有了记忆，Agent 可以积累知识、记住用户偏好、跨任务保持上下文。

## 7. RAG（检索增强生成）

### 是什么
Retrieval-Augmented Generation。让 LLM 先"查资料"再"回答问题"，而不是全靠训练时的记忆。

### 工作流程
```
用户提问
    ↓
从知识库检索相关文档（检索）
    ↓
把检索结果拼到 Prompt 里（增强）
    ↓
LLM 基于检索结果生成回答（生成）
```

### 为什么需要 RAG
- LLM 的训练数据有截止日期，不知道最新信息
- LLM 会"幻觉"（编造不存在的事实）
- RAG 让 LLM 基于实际文档回答，可溯源

### 你的项目里
`DeepExtractor` 从 PDF 提取文本 → 拼到 User Message → LLM 输出六维分析。这就是 RAG 的雏形。

## 8. Chain vs Agent（链 vs 智能体）

### 常见误解
**Chain 也能调用 Tool。** 你的 `academic-self` 就是证明——它调了 DeepSeek API、PDF 提取器、SQLite、文件移动——每步都是工具调用，但每一步的顺序是代码写死的。

### 真正的区别：谁在决策

| | Chain（链） | Agent（智能体） |
|------|-----------|------------|
| **能用 Tool 吗** | 能 | 能 |
| **谁决定调哪个 Tool** | 程序员写死顺序 | LLM 自己判断 |
| **流程是否可变** | 固定 | 动态 |
| **灵活性** | 低，但可靠、可预测 | 高，但可能跑偏或循环 |
| **适合场景** | 明确、重复的工作流 | 开放性的探索任务 |

### 比喻
```
Chain  = 地铁 —— 轨道固定，准时可靠，但只能按线路走
Agent = 出租车 —— 根据路况变道，灵活应变，但可能走错路
```

### 实际对比
```
Chain 方式：
  采集 → 处理 → 入库
  （搜API）→（翻译）→（存SQLite）
  三个工具都调了，但顺序写死，处理完就结束

Agent 方式：
  用户："这篇论文值得精读吗？"
  → LLM 决定先调搜索工具找论文
  → 看了摘要不够，再决定调深度分析工具
  → 分析完觉得需要对比，再决定调相似论文检索
  → 每一步都是 LLM 自己判断要不要继续、调什么
```

### 你的 academic-self 是什么
**能调 Tool 的 Chain。** 没有自主决策能力——每一步都是代码写好的。但 Prompt + 工具 + 记忆三层结构已是 Agent 的骨架。

### 一句话总结
> Chain 和 Agent 都能用工具。区别在于"谁决定下一步"——是代码还是 LLM。

## 10. Orchestration（编排层）

### 是什么
Agent 系统的"调度中心"。负责管理除 LLM 推理之外的所有事情。

### 三个角色
```
在 Multi-Agent 中 → 负责把任务分给不同的 Agent，汇总结果
在单 Agent 中   → 负责选取 LLM、调用 Tool、管理记忆
在 Chain 中     → 按写死的顺序依次执行步骤
```

### 编排层做了什么
```
用户输入
    │
    ▼
┌────────────── 编排层 ──────────────┐
│                                    │
│  1. 管理对话历史（短期记忆读写）    │
│  2. 调用 LLM 进行推理              │
│  3. 解析 LLM 返回的 Tool Call 指令 │
│  4. 执行对应的工具函数             │
│  5. 把工具结果传回给 LLM           │
│  6. 读写长期记忆（数据库/向量库）  │
│  7. 判断是否继续循环还是返回结果   │
│                                    │
└────────────────────────────────────┘
    │
    ▼
最终回复给用户
```

### 为什么这是核心
**Chain vs Agent 的本质差异就在编排层。**
- Chain 的编排层：代码写死的 if-else 流程
- Agent 的编排层：LLM 参与决策的循环

### 在 Dify 里
编排层被可视化成了**拖拽式的流程图**——你不用写代码，用节点连线就能设计上述整个调度逻辑。这就是为什么 Dify 适合作为学习 Agent 的入门工具。

## 小结

| 术语 | 一句话 |
|------|--------|
| LLM | 预测下一个 Token 的推理引擎 |
| Token | LLM 认知世界的最小单位 |
| Prompt | 你和 LLM 沟通的方式（System=角色规则，User=数据指令） |
| Context Window | LLM 一次能看到的文本上限 |
| Tool Call | LLM 操作外部世界的手，Chain 和 Agent 都能用 |
| Memory | 跨时间记住信息：短期（会话上下文）+ 长期（知识库） |
| RAG | 先从知识库检索，再让 LLM 基于检索结果生成回答 |
| Chain | 代码写死的流水线，用 Tool 但顺序固定，稳定可靠 |
| Agent | LLM 自主决策的智能体，灵活但有不确定性 |
| Orchestration | 调度中心，管理 LLM/Tool/Memory 的协作，Chain vs Agent 的本质差异在这里 |
| Multi-Agent | 多 Agent 分工协作，像公司的组织架构 |

## 9. Multi-Agent（多智能体）

### 是什么
多个 Agent 分工协作，像一家公司的组织架构：

```
          老板 Agent（分配任务、汇总结果）
              │
    ┌─────────┼─────────┐
    │         │         │
  研究员    翻译员    审稿人
  (搜文献)  (翻译)   (深度分析)
```

### 为什么需要 Multi-Agent
- 单个 Agent 的上下文窗口有限，任务多了会"分心"
- 不同 Agent 可以有不同的 System Prompt 和工具
- 专业化分工 = 每个 Agent 做得更好

### 你的项目可能的 Multi-Agent 设计
```
采集 Agent：每周自动搜索 WOS API，入库新文献
筛选 Agent：快速浏览新文献，标记有用/待定
精读 Agent：对有用文献做六维深度提取
简报 Agent：每月生成领域动态简报
```

# 第二站：Agent 的运行原理

---

## 核心问题

一个 Agent 到底是怎么"思考"和"行动"的？它不是一个黑箱——它遵循一套明确的循环模式。

---

## 1. 思考-行动-观察 循环

### 这是 Agent 运行的底层引擎

```
         ┌──────────────────────────────────┐
         │                                  │
         ▼                                  │
    ┌─────────┐    ┌─────────┐    ┌─────────┐
    │  Think  │ →  │  Act    │ →  │ Observe │
    │  思考   │    │  行动   │    │  观察   │
    └─────────┘    └─────────┘    └─────────┘
         │                              │
         └──────────────────────────────┘
                    循环
```

### 每一步做了什么

| 阶段 | 英文 | 做什么 | 谁执行 |
|------|------|--------|--------|
| **思考** | Think | 分析当前情况，决定下一步做什么 | LLM |
| **行动** | Act | 执行决策（调用工具 / 输出回复） | 编排层 |
| **观察** | Observe | 把行动结果反馈给 LLM，判断是否完成 | 编排层 |

### 一个完整例子

```
用户："帮我找3篇关于动态办公椅的最新论文，翻译摘要"

第1轮循环：
  Think  → "用户要论文，我需要先搜索。调用搜索工具查 'dynamic office chair'"
  Act    → 编排层执行 tool_search("dynamic office chair")
  Observe → 返回了 15 篇论文列表

第2轮循环：
  Think  → "搜到15篇，取最近3篇。但我没有它们的摘要，需要读取论文详情"
  Act    → 编排层执行 tool_get_paper_detail(id=1), tool_get_paper_detail(id=2), tool_get_paper_detail(id=3)
  Observe → 返回3篇完整信息（含英文摘要）

第3轮循环：
  Think  → "有摘要了，需要翻译。调用翻译工具"
  Act    → 编排层执行 tool_translate(paper1), tool_translate(paper2), tool_translate(paper3)
  Observe → 返回3篇中文摘要

第4轮循环：
  Think  → "任务完成，整理结果回复用户"
  Act    → 输出最终回复
  Observe → 无（结束）
```

## 2. ReAct 模式

### 是什么
ReAct = **Rea**soning + **Act**ing。是目前 Agent 开发最主流的设计模式。

### 核心思想
让 LLM 在每一步同时输出两样东西：
1. **推理过程**（Reasoning）："我现在应该……因为……"
2. **具体行动**（Action）：调用哪个工具，参数是什么

### 举例
```
用户："这篇论文的影响因子是多少？"

LLM 的输出：
  Thought: 用户问影响因子，我需要先查到这篇论文。但我不知道是哪篇，需要问用户或搜索。

  Thought: 我先假设用户指的是上次提到的那篇动态办公椅论文。
           我先查数据库里有没有记录。

  Action: tool_search_database("动态办公椅")
  Observation: 找到1篇，doi=10.1016/j.apergo.2024.01.003，无JIF字段

  Thought: 数据库里没有影响因子。需要调 WOS API 查询。

  Action: tool_query_wos("10.1016/j.apergo.2024.01.003")
  Observation: JIF=3.7, Q1, Ergonomics学科排名 4/16

  Thought: 查到了，JIF 3.7，可以告诉用户了。

  Final Answer: 这篇 Applied Ergonomics 上的论文，影响因子 3.7，
               在 Ergonomics 学科排名 Q1（第4/16位）。
```

### 关键理解：ReAct 不是"先全盘规划再执行"

**错误理解**：LLM 先把任务拆成完整路线图，然后一步步执行。
**实际机制**：LLM 想一步、走一步、看结果、再决定下一步。

```
错误模型：                        正确模型（ReAct）：
规划 Step1,2,3,4  →  执行到底     Think → Act → Observe
                                  → 根据结果重新 Think
                                  → 再 Act → 再 Observe
                                  → 直到完成
```

每一步的方向取决于上一步的结果——这就是 Agent 比 Chain 灵活的原因，也是 Agent 有"不确定性"的原因。

> 比喻：Chain 是按导航走，路线提前定好了。Agent 是在迷雾里走，走一步看一眼地图，再决定下一步往哪。

### 为什么 ReAct 好
- **可解释**：你能看到 LLM 的推理链，知道它为什么这么做
- **可调试**：哪一步推理错了，一看就知道
- **减幻觉**：LLM 写推理过程时会"自我审查"，减少乱来的概率

## 3. 工具调用机制

### 工具是怎么被 LLM "看到"的

在每个 Agent 的 System Prompt 里，工具是以**函数说明书**的形式给出的：

```
# 可用工具

## tool_search_paper
用途：搜索论文
参数：
  - keyword (string, 必填): 搜索关键词
  - year (string, 选填): 年份限制
  - limit (integer, 选填): 最大返回数，默认10
返回：论文列表 [{title, authors, doi, year, abstract}]

## tool_translate
用途：翻译英文摘要为中文
参数：
  - text (string, 必填): 要翻译的英文文本
返回：{title_cn: string, abstract_cn: string}
```

LLM 读到这些 Tool 定义后，就知道"我能做什么"。当它推理出需要调用某个工具时，它会输出结构化的调用指令：

```json
{
  "tool": "tool_search_paper",
  "arguments": {
    "keyword": "dynamic office chair",
    "year": "2024",
    "limit": 5
  }
}
```

### 完整流程

```
1. System Prompt 里写好"你有以下工具可用：..."
2. 用户提问
3. LLM 分析 → 决定调 tool_search_paper → 输出调用指令（JSON）
4. 编排层解析 JSON → 执行对应的 Python 函数 → 拿到结果
5. 编排层把结果拼成新消息："工具返回的结果是：[结果]"
6. 返回给 LLM
7. LLM 看结果 → 决定下一步（继续调其他工具 / 回复用户）
8. 循环直到 LLM 认为任务完成
```

## 4. 记忆的读写时机

### 三种记忆的明确区分

| | 短期记忆 | 工作记忆 | 长期记忆 |
|------|---------|---------|---------|
| **存什么** | 你和 Agent 的对话内容 | 当前任务的执行进度 | 持久化的知识和偏好 |
| **举例** | "你刚才说要搜动态办公椅" | "正在处理第15/42篇，成功了12篇" | 890篇文献的数据库 |
| **谁在用** | LLM（理解上下文） | 编排层（控制流程） | LLM + 编排层（按需调取） |
| **存活时间** | 一次会话 / Context内 | 单次任务结束即丢 | 永久（直到手动删除） |
| **跨项目** | 不跨（随会话绑定） | 不跨（A项目看不到B项目的进度） | 可跨（知识库是所有项目共享的） |

### 短期记忆（对话上下文）

```
第1轮对话 ──→ 存入历史
第2轮对话 ──→ 存入历史
第3轮对话 ──→ 存入历史
    │
    ▼
每次调用 LLM 时，把完整的对话历史塞进 messages 数组
    │
    ▼
当历史超过 Context Window → 最旧的被截断（遗忘）
    │
    ▼
补救方法：对旧对话做摘要提炼，存入长期记忆
```

### 工作记忆（执行进度）

```
不持久化。只在单次任务运行期间存在。
比如：批处理循环里的计数器、已处理的论文 ID 列表。
任务结束就丢，且A项目的进度信息不会出现在B项目中。

工作记忆的关键特征：
- 给编排层用的，不是给 LLM 看的
- 你可以选择把工作记忆的摘要存入短期记忆（告诉 LLM "刚才处理到哪了"）
- 但工作记忆本身不直接参与 LLM 推理
```

### 长期记忆（知识库）

```
写操作：LLM 决定"这个信息以后会用到"
    → 调用 tool_save_memory(key="用户偏好", value="关注动态座椅方向")
    → 编排层存入数据库

读操作：LLM 决定"我需要回忆一些信息"
    → 调用 tool_search_memory("动态座椅")
    → 编排层从数据库检索 → 拼入当前 Prompt

长期记忆可以通过 RAG 被精准检索调用。
```

## 5. Chain 的循环 vs Agent 的循环

两者都在循环，但循环里的决策者不同：

```
Chain 的循环：                    Agent 的循环：
┌─────────────────┐              ┌─────────────────┐
│ 代码决定的循环   │              │ LLM 决定的循环   │
│                 │              │                 │
│ for paper in    │              │ while not done: │
│   papers:       │              │   LLM推理→调工具 │
│   翻译(paper)   │              │   →观察→再推理   │
│   入库(paper)   │              │   →判断是否完成  │
│                 │              │                 │
│ 固定循环N次     │              │ 循环次数不确定   │
│ 每步100%可预测  │              │ 每步由LLM动态决定│
└─────────────────┘              └─────────────────┘
```

## 6. Orchestration 到底在哪？

### 关键理解：Orchestration 不是流程中的一步——它是承载所有步骤的容器

```
                        时间线 →
    ╔═══════════════════════════════════════════════════════════╗
    ║                   Orchestration（一直在运行的容器）        ║
    ║                                                           ║
    ║   moment 1          moment 2          moment 3            ║
    ║   ┌────────┐       ┌────────┐       ┌────────┐           ║
    ║   │构建    │  →    │调用    │  →    │执行    │  → ...    ║
    ║   │Messages│       │LLM     │       │Tool    │           ║
    ║   └────────┘       └────────┘       └────────┘           ║
    ║        ↑               ↑               ↑                 ║
    ║        │               │               │                 ║
    ║   它负责组装       它负责把       它负责拿到              ║
    ║   提示词发给       LLM 的指令      LLM 的 JSON           ║
    ║   LLM             传给 LLM        转成函数调用           ║
    ║                                                           ║
    ╚═══════════════════════════════════════════════════════════╝
```

### 用你的 academic-self 来解释

你的 `server.py` 的函数就是 Orchestration 的一小部分：

```python
# server.py 里的每个路由，都是在手动做 Orchestration 的事
@app.post("/api/process-one/{lit_id}")
async def api_process_one(lit_id: int):
    paper = kb.get_paper_by_id(lit_id)       # ← Orchestration: 从记忆读数据
    result = ai.process_one(paper)            # ← Orchestration: 调用 LLM
    kb.set_processed(lit_id, result)          # ← Orchestration: 把结果写回记忆
    return {"ok": True}
```

它不是"某一步"——它是**把每一步串起来的那个东西**。

### 更准确的比喻

| | Orchestration 是什么 |
|------|------|
| 它不是 | 第一步、第二步、第三步……流程里的某个环节 |
| 它是 | 一个**while 循环**，不断重复 "调LLM→解析→执行→反馈→再调LLM"，直到任务完成 |
| 它不是 | 厨师长（参与做菜的人） |
| 它是 | 厨房（锅碗瓢盆灶台水管，所有东西都在厨房里运转） |

### 全链路视角

```
用户输入："这篇论文值不值得精读？"

╔═══════════ Orchestration（这个 while 循环一直在跑）═══════════╗
║                                                               ║
║  while 任务未完成:                                            ║
║      │                                                        ║
║      ├─ ① 组装 Messages:                                      ║
║      │     [System + 工具列表] + [历史对话] + [当前输入]       ║
║      │                                                        ║
║      ├─ ② 调用 LLM ─────────────────────┐                     ║
║      │                                   │                    ║
║      │     LLM 推理：                     │                    ║
║      │     "我没看到论文信息，得先搜索"    │  ← LLM 在自己的    ║
║      │     输出: tool_call("search")      │     黑盒里思考     ║
║      │                                   │                    ║
║      ├─ ③ 解析 LLM 输出 ←────────────────┘                    ║
║      │     "LLM 说要调 search，参数是..."                     ║
║      │                                                        ║
║      ├─ ④ 执行工具:                                            ║
║      │     运行 search_paper() → 返回 [{title, doi}]          ║
║      │                                                        ║
║      ├─ ⑤ 把工具结果传回 LLM:                                  ║
║      │     Messages 追加: [Tool Result] "找到1篇..."          ║
║      │                                                        ║
║      ├─ ⑥ 再次调用 LLM ─────────────────┐                     ║
║      │                                   │                    ║
║      │     LLM 推理：                     │                    ║
║      │     "有DOI了，可以深度分析了"      │                    ║
║      │     输出: tool_call("deep_analyze")│                    ║
║      │                                   │                    ║
║      ├─ ⑦ 再次解析+执行+反馈... ←────────┘                    ║
║      │                                                        ║
║      ├─ ...循环第3轮、第4轮...                                 ║
║      │                                                        ║
║      └─ ⑧ LLM 最终输出文字回复 → while 结束                    ║
║            同时把分析结果写入长期记忆                           ║
║                                                               ║
╚═══════════════════════════════════════════════════════════════╝
                                                              │
                                                              ▼
                                                    把最终回复展示给用户
```

### 一句话总结

> **Orchestration 是一个 while 循环。** 每次循环做三件事：调 LLM → 解析 LLM 的指令 → 执行指令（调工具或返回结果）。它不在流程里，它就是流程本身。

## 7. 常见误解纠正

### 误解 1："ReAct 是先规划完整路线再执行"
**实际**：ReAct 是想一步、走一步、看结果、再决定下一步。它不会提前规划完整路线——每一步的方向取决于上一步的结果。

### 误解 2："工作记忆 = 短期记忆"
**实际**：是两个独立概念。
- 短期记忆：给 LLM 看的对话内容，受 Context Window 限制
- 工作记忆：给编排层用的执行进度，任务结束即丢
- A 项目的工作记忆不涉及 B 项目；但短期记忆提炼后存入长期记忆是可以跨项目的

### 误解 3："Chain 不能调用 Tool"
**实际**：Chain 也能调用 Tool。你的 `academic-self` 就是证明。区别在于谁决定调哪个 Tool——代码写死 vs LLM 自主判断。

### 误解 4："Orchestration 是流程中的某一步"
**实际**：Orchestration 是一个 while 循环，它不在流程里，它就是流程本身。它相当于 Agent 的"操作系统"。

## 小结

| 概念 | 一句话 |
|------|--------|
| 思考-行动-观察 | Agent 运行的底层循环引擎，不是一次性规划 |
| ReAct | 想一步走一步看结果再想下一步，不是全盘规划 |
| 工具定义 | 工具以"说明书"形式贴在 System Prompt 里 |
| 工具调用流程 | LLM 输出 JSON → 编排层执行 → 结果反馈 → LLM 再决策 |
| 短期记忆 | 给 LLM 看的对话上下文，受 Context Window 限制 |
| 工作记忆 | 给编排层用的执行进度，任务结束即丢，不跨项目 |
| 长期记忆 | 持久化知识库，RAG 检索调用，可跨项目共享 |
| Chain 循环 vs Agent 循环 | 都是循环，区别在于循环路径谁决定 |
| Orchestration | 一个 while 循环——不停做"调LLM→解析→执行→反馈" |

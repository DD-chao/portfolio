# 第三站：设计原则

---

## 核心问题

有了大脑（LLM）、有了手（Tool）、有了记忆（Memory）、有了调度系统（Orchestration），怎么把这些拼成一个**靠谱**的 Agent？

这不是简单的堆砌——设计不好的 Agent 会跑偏、会幻觉、会死循环、会浪费 Token。

---

## 1. 角色定义

### 原则：角色越具体，行为越稳定

| 坏的写法 | 好的写法 | 为什么 |
|----------|---------|--------|
| "你是一个助手" | "你是工业设计/人因工程领域的英中学术翻译专家" | 领域+角色+专长，模型知道调用哪个知识区 |
| "帮我分析论文" | "你是审稿人，六维度分析：研究问题/方法/流程/发现/局限/引用价值" | 具体任务拆解，模型知道输出什么结构 |
| 不写边界 | "只分析给定论文，不评价作者、不推荐期刊、不建议引用" | 负面约束防止模型"多管闲事" |

### 一个完整的角色定义模板

```
# 角色
你是 [具体领域] 的 [具体角色]，专长于 [1-2个核心能力]。

# 你的工作方式
- 你会做 [A]
- 你也会做 [B]
- 你不会做 [X]、[Y]、[Z]

# 输出要求
- 格式：[具体格式]
- 语言：[语言要求]
- 长度：[字数限制]
```

## 2. 任务拆解

### 原则：给 LLM 的任务应该像给实习生的任务

> 实习生能做好一件事，但你要把一件大事拆成几件小事，每件说清楚。

| 坏的拆解 | 好的拆解 |
|----------|---------|
| "帮我研究一下动态办公椅" | ① 搜索近3年动态办公椅论文 ② 筛选影响因子>2的 ③ 逐篇翻译摘要 ④ 标注每篇的研究方法和样本量 |
| "写一篇文献综述" | 太复杂，单次调用无法完成。需要 Chaining 或多 Agent |

### 任务拆解的判断标准

如果一个任务满足以下条件，可以交给单次 LLM 调用：
- 输入明确（有一篇论文 + 有摘要）
- 输出明确（六维 JSON）
- 不需要外部信息
- 预期输出长度在 max_tokens 范围内

如果超过以上任何一条，就需要拆成多步或交给 Agent 循环。

## 3. 防幻觉设计

### Agent 最容易产生幻觉的三种情况

| 情况 | 举例 | 防御方法 |
|------|------|---------|
| **信息缺失** | 论文没有摘要，LLM 根据标题编了一个 | 规定兜底输出："（无摘要）" / "本文未明确说明" |
| **知识过期** | LLM 不知道某期刊2024年改名了 | 用 RAG / Tool Call 查实时数据，不要靠 LLM 记忆 |
| **过度推理** | "这篇论文说 A 比 B 好，所以 A 一定是最好的" | 要求 LLM 区分"原文结论"和"你的推断" |

### 你的项目的防幻觉设计

```python
# 你在 DEEP_SYSTEM_PROMPT 里写的这条就是标准的防幻觉规则：
"若某维度原文确实没有相关内容，填'本文未明确说明'"
"若摘要缺失，summary 填'（无摘要）'"
"若连正文都没有，所有字段填'（全文缺失，无法提取）'"
```

这三个 if-else 覆盖了所有边界情况。好的防幻觉设计就是**让 LLM 在任何输入下都知道该输出什么，不给它留"自由发挥"的空间。**

## 4. 容错与兜底

### 原则：不要假设 LLM 永远正确

LLM 的输出是不可靠的——格式可能错、JSON 可能断、内容可能跑偏。做好三层兜底：

```
第一层：Prompt 约束（预防）
  "直接返回JSON，不要其他内容"  ← 减少格式错误概率

第二层：代码兜底（检测）
  try: json.loads(text)
  except: 提取 "{...}" 部分再试  ← 处理 markdown 代码块包裹

第三层：降级策略（止损）
  如果 JSON 完全解析不了 → 把原始文本当纯文本存 → 标记"需人工检查"
  不要因为一篇论文解析失败就让整个批次崩溃
```

### 三层兜底详解

#### 第一层：Prompt 约束（预防）

通过 Prompt 限制 LLM 的发散思考，从源头减少出错。

```
不做约束时：
  LLM 可能输出："好的，这是翻译结果...（500字废话）...{JSON}...希望对你有帮助！"

约束后：
  "直接返回JSON，不要其他内容" → LLM 输出：{JSON}
```

比喻：跟 LLM 说"答完就走，别加戏"。LLM 自我约束。

#### 第二层：代码兜底（止损）

LLM 还是加了戏？代码自己动手擦掉，不崩溃。

```python
text = llm_response

# 尝试理想情况：直接解析
try:
    result = json.loads(text)
except json.JSONDecodeError:
    # 抢救：剥掉 markdown 代码块标记
    if text.startswith("```"):
        lines = text.split("\n")
        text = "\n".join(lines[1:-1])  # 去掉首尾 ``` 行
        try:
            result = json.loads(text)   # 再试
        except:
            # 还是不行 → 兜底，不崩溃
            result = {"abstract_cn": text[:500], "key_points": []}
```

代码层是**清洁工，不是编辑**——只擦灰（去掉包裹的废话），不改内容（不动 LLM 的实际输出）。擦不干净就留原始文本兜底，标记"需人工检查"。

#### 第三层：人工兜底（补漏）

第二天看日志，发现标记出来的失败条目，手动处理。前两层顶住了批量任务的大部分问题，人工只需要处理极少数顽固情况。

## 5. 循环控制

### Agent 独有的问题：死循环

Chain 不会死循环——因为步骤数是写死的。但 Agent 会——LLM 可能陷入"调工具→不满意→再调→还不满意→再调..."。

### 防御策略

| 策略 | 做法 |
|------|------|
| **最大步数** | 限制 Agent 最多循环 10 轮，超过就强制结束并报告"当前进度：[...]" |
| **超时检测** | 整个任务超过 60 秒就终止 |
| **重复检测** | 如果 LLM 连续 3 次调用同一个工具且参数相同 → 拦截并引导它换方向 |
| **Token 预算** | 总 Token 消耗超过阈值 → 截断历史 → 提醒用户 |

## 6. 安全边界

### 什么不该让 Agent 做

| 不应该 | 原因 | 替代方案 |
|--------|------|---------|
| 直接删除数据 | LLM 可能判断错误 | 标记"待删除"，人工确认后再删 |
| 发送邮件/消息 | 可能发错人/发错内容 | 生成草稿，人工审核后发送 |
| 修改自身 Prompt | 会被 prompt injection 攻击 | 核心 Prompt 放在代码里，不让 LLM 读写 |
| 执行任意 Shell 命令 | 极其危险 | 只开放几个预定义的"安全函数" |

### 你的项目里一个隐含的安全风险

你的 `config.json` 里硬编码了 API 密钥。如果有人通过 prompt injection 让 Agent "读取配置文件"，密钥就泄露了。修复方式：把密钥移到环境变量，Agent 根本不知道密钥在哪。

## 7. 设计清单（每次设计 Agent 时过一遍）

```
□ 角色：是否具体到了领域+角色+专长？
□ 边界：是否明确了"不做的事"？
□ 格式：是否给出了完整的输出示例（不只是文字说明）？
□ 防幻觉：是否为所有"信息缺失"情况规定了兜底输出？
□ 容错：JSON 解析失败时有 fallback 吗？单条失败会影响全局吗？
□ 循环控制：最大步数、超时、重复检测设了吗？
□ 安全：Agent 能操作的范围是否被限制在安全函数内？
□ 成本：有没有关掉非必要任务的 thinking？temperature 设对了吗？
```

## 小结

| 原则 | 核心 |
|------|------|
| 角色定义 | 越具体越稳定。领域+角色+专长+边界 |
| 任务拆解 | 一件大事拆成几件小事，每件说清楚 |
| 防幻觉 | 堵住所有"信息缺失"的漏洞，不让 LLM 自由发挥 |
| 容错兜底 | Prompt约束→代码检测→降级止损，三层防护 |
| 循环控制 | Agent 独有的风险：最大步数+超时+重复检测 |
| 安全边界 | 删除/发送/执行/自我修改 → 都需要人工闸门 |
